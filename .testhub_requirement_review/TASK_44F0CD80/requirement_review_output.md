## 📝 逐条问题详情与改善建议

### 问题 1：FR3.4 与范围声明矛盾

**位置：** 第1章「1.3 目标与范围」/ 第3章「3.1.3 第三方账号授权登录」FR3.4  
**严重级别：** P0  
**涉及维度：** 逻辑一致性（扣5分）

**原文摘录：**
> 1.3 范围：不包含：用户个人资料编辑、账户安全设置（如修改手机号、绑定微信等），这些将列入后续版本规划。

> FR3.4：如果是新用户，则要求其补充设置用户名（或使用第三方昵称）并完成注册。（注意：为简化流程，可跳过设置密码环节，后续可在账户安全中设置）

**问题描述：**
文档在范围中明确将"账户安全设置"排除在本阶段之外，但FR3.4却引导用户"后续可在账户安全中设置"密码。这会导致开发团队对范围产生歧义：账户安全设置功能到底做不做？如果不做，第三方登录用户的密码设置入口在哪里？

**改善建议（具体可执行）：**

**[建议方案 A — 推荐]**  
修改 FR3.4 为：
> 如果是新用户，则要求其补充设置用户名（或使用第三方昵称）并完成注册。第三方登录用户暂不强制设置密码，密码设置功能随"账户安全"模块在后续版本提供。

**修改说明：**
- 明确了本阶段第三方登录用户确实不设置密码
- 删除了"后续可在账户安全中设置"的引导性表述，避免与范围声明冲突
- 如需保留密码设置能力，需先将"账户安全设置"纳入本阶段范围

**[建议方案 B — 备选]**  
如果业务上确实需要在本阶段提供密码设置入口：
> 将 1.3 范围修改为：本阶段需求涵盖：...、第三方授权登录、忘记密码、登录状态管理、**账户安全设置（仅限密码设置）**等功能。

### 问题 2：自动注册场景协议勾选要求不一致

**位置：** 第3章「3.1.1 手机号注册」FR1.7 / 「3.2.2 短信验证码登录」FR5.3  
**严重级别：** P0  
**涉及维度：** 逻辑一致性（扣5分）

**原文摘录：**
> FR1.7：用户阅读并勾选《用户协议》和《隐私政策》后方可注册。

> FR5.3：未注册：自动为该手机号创建账户并登录（需弹窗告知用户并请求同意用户协议）。

**问题描述：**
手机号注册时要求同时同意《用户协议》和《隐私政策》，而短信验证码登录自动注册时仅要求同意《用户协议》。这会导致合规风险（隐私政策未获同意）和逻辑不一致（两种注册路径的合规标准不同）。

**改善建议（具体可执行）：**

**[建议方案 A — 推荐]**  
修改 FR5.3 为：
> 未注册：自动为该手机号创建账户并登录（需弹窗告知用户并请求同意《用户协议》和《隐私政策》，提供勾选框和文档链接）。

**修改说明：**
- 统一两种注册方式的协议勾选要求，确保合规性一致
- 弹窗需同时展示两个协议的勾选框和超链接

### 问题 3：缺少验收标准

**位置：** 全文  
**严重级别：** P1  
**涉及维度：** 可测试性（扣5分）

**问题描述：**
文档缺少独立的"验收标准"章节，测试人员无法直接依据需求编写测试用例的通过/失败判定标准。虽然部分功能需求包含了预期行为，但缺乏可量化的验收条件。

**改善建议（具体可执行）：**

**[建议方案 A — 推荐]**  
在文档中新增第6章「验收标准」，为每条功能需求补充验收标准。示例：

| 需求编号 | 验收标准 |
|---------|---------|
| FR1.2 | 输入12位数字时前端提示"请输入11位手机号码"；输入非1开头的11位数字时提示"手机号格式错误" |
| FR1.3 | 点击"获取验证码"后，系统调用短信服务商接口，返回发送成功状态 |
| FR1.4 | 同一手机号60秒内重复点击，按钮置灰并倒计时60秒，提示"请60秒后重试" |
| FR1.6 | 输入7位密码提示"密码至少8位"；输入纯数字密码提示"密码需包含字母"；输入纯字母密码提示"密码需包含数字" |
| FR1.9 | 注册成功后，数据库用户表新增一条记录，状态为"已激活"；客户端收到JWT Token并跳转至首页 |

**修改说明：**
- 每条验收标准需包含：触发条件、操作步骤、预期结果、判定标准
- 验收标准应可独立验证，不依赖其他需求

### 问题 4：用户名规则缺失

**位置：** 第3章「3.1.3 第三方账号授权登录」FR3.4  
**严重级别：** P1  
**涉及维度：** 清晰无歧义（扣3分）

**原文摘录：**
> FR3.4：如果是新用户，则要求其补充设置用户名（或使用第三方昵称）并完成注册。

**问题描述：**
文档要求用户"补充设置用户名"，但未定义用户名的长度限制、允许字符、唯一性要求等规则。开发和测试无法确定合法用户名的边界。

**改善建议（具体可执行）：**

**[建议方案 A — 推荐]**  
修改 FR3.4 为：
> 如果是新用户，则要求其补充设置用户名（或使用第三方昵称）并完成注册。用户名规则：2-20个字符，支持中文/字母/数字/下划线，不允许纯数字，需全局唯一。如用户不填写，默认使用第三方昵称（需过滤特殊字符，长度超出时截断至20字符）。

**修改说明：**
- 明确了长度、字符类型、唯一性三大核心规则
- 给出了默认值的生成逻辑

### 问题 5：密码规则不完整

**位置：** 第3章「3.1.1 手机号注册」FR1.6  
**严重级别：** P1  
**涉及维度：** 清晰无歧义（扣2分）

**原文摘录：**
> FR1.6：用户需设置登录密码（需输入两次）。密码规则：至少 8 位，需包含字母和数字。

**问题描述：**
密码规则缺少关键细节：是否区分大小写？是否允许/必须包含特殊字符？最大长度是多少？这些缺失会导致前端校验规则不统一。

**改善建议（具体可执行）：**

**[建议方案 A — 推荐]**  
修改 FR1.6 为：
> 用户需设置登录密码（需输入两次，两次需一致）。密码规则：长度 8-20 位，需同时包含大写字母、小写字母和数字，不允许包含空格。

**修改说明：**
- 明确了长度范围（8-20位）
- 明确了大写、小写、数字的组合要求
- 明确了空格限制

**[建议方案 B — 备选]**  
如果业务不要求大小写混合：
> 密码规则：长度 8-20 位，需同时包含字母（不区分大小写）和数字，不允许包含空格。

### 问题 6：Token有效期表述模糊

**位置：** 第3章「3.4 登录状态维护」FR7.4  
**严重级别：** P1  
**涉及维度：** 清晰无歧义（扣2分）

**原文摘录：**
> FR7.4：Token 应设置有效期（如 7 天）。提供 Refresh Token 机制以在用户活跃时无感刷新登录状态。

**问题描述：**
"如7天"表示这是示例还是确定值？测试人员无法确定Token过期时间应按7天测试还是按其他值测试。

**改善建议（具体可执行）：**

**[建议方案 A — 推荐]**  
修改 FR7.4 为：
> Token 有效期设置为 7 天。提供 Refresh Token 机制：用户每次活跃操作时，如 Token 剩余有效期不足 2 天，自动刷新为新 Token（有效期重新计算为 7 天）。

**修改说明：**
- 将"如7天"改为确定值"7天"
- 补充了Refresh Token的触发条件（剩余不足2天）

### 问题 7：第三方登录异常处理缺失

**位置：** 第3章「3.1.3 第三方账号授权登录」FR3.2-FR3.5  
**严重级别：** P1  
**涉及维度：** 边界与异常处理（扣3分）

**问题描述：**
文档只描述了第三方登录成功的流程，未覆盖以下异常场景：
- 用户在第三方页面取消授权
- 第三方服务不可用（如微信服务器故障）
- 第三方返回的用户信息不完整（无OpenID/UnionID）
- 授权超时

**改善建议（具体可执行）：**

**[建议方案 A — 推荐]**  
在 FR3.5 后补充异常处理需求：

> FR3.6：用户取消授权或授权超时（超过5分钟）时，返回登录页，不提示错误。
> FR3.7：第三方服务不可用或返回异常时，提示"第三方登录服务暂不可用，请尝试其他登录方式"。
> FR3.8：第三方未返回有效OpenID/UnionID时，提示"获取第三方信息失败，请重试"，并记录错误日志。

**修改说明：**
- 区分了用户主动取消（无错误提示）和系统异常（有错误提示）
- 明确了超时时间（5分钟）

### 问题 8：忘记密码时未注册账号的处理缺失

**位置：** 第3章「3.3 忘记密码」FR6.2  
**严重级别：** P1  
**涉及维度：** 边界与异常处理（扣2分）

**原文摘录：**
> FR6.2：用户需输入已注册的手机号/邮箱。

**问题描述：**
文档假设用户输入的是已注册账号，但未说明如果用户输入未注册的手机号/邮箱时应如何处理。

**改善建议（具体可执行）：**

**[建议方案 A — 推荐]**  
在 FR6.2 后补充：

> FR6.2a：如输入的手机号/邮箱未注册，提示"该账号未注册，请先注册"，并提供"去注册"按钮跳转至注册页。

**修改说明：**
- 明确提示文案，避免用户困惑
- 提供跳转入口，缩短用户路径

**[建议方案 B — 备选]**  
出于安全考虑（防止枚举攻击）：
> FR6.2a：如输入的手机号/邮箱未注册，同样提示"验证码已发送"（实际不发送），避免暴露账号是否存在。
